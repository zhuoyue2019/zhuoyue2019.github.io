# 3GPP TS 24.481 解读：MC 组管理——一个群谁建、谁管、谁能进

> 版本：v1.0 ｜ 更新：2026-10-28 ｜ 基线：TS 24.481 v19.1.0（Rel-19，2025-09）｜ 原文：whatthespec.net 抓取的关键条款


**TS 24.481 是 MCX 的组管理协议，规定群组怎么建、成员怎么加减、配置怎么变 [§1]。**

## 1. 它要解决什么问题

咱们平时建个聚餐群，拉几个人、起个名、发条消息，一个人一分钟内就搞定了。但请想象一下消防队的现场：一个城市有成百上千个作战小组，队员换班频繁、任务区域随时调整，每个组还有自己的通话权限、调度配置。如果全靠人工一个一个群去建、一个一个成员去改，光配置就要忙到天亮，而且极易出错——某个已撤离的队员还留在通话组里，后果不堪设想 [§1]。

于是标准要回答的问题很实在：

- **群太多、建不过来**：成百上千个群，必须让机器按协议自动建，而不是人肉点手机 [§1]。
- **人太多、管不过来**：成员进出要有标准流程，谁有权限把谁拉进来、把谁踢出去 [§6.3.2]。
- **配置要一致**：每个群的参数（比如成员名单）不能有人手动写错，必须用统一的“配置文件”来管 [§6.3]。
- **变更要通知到人**：群里改了配置，相关的人要第一时间知道，不能等开会时才口头通知 [§6.3]。

这份规范管的，就是这套“建群、管人、改配置”的标准化动作 [§1]。

## 2. 它在 MCX 家族中的位置

3GPP 制定一个功能，通常分三步走：先写“要什么”（Stage 1 需求），再写“怎么分角色”（Stage 2 架构），最后写“具体怎么说话”（Stage 3 细节协议）。TS 24.481 就是 Stage 3 的协议细节规范，对象很明确：支持组管理客户端（GMC）功能的用户设备（UE）、支持组管理服务器（GMS）功能的应用服务器，以及支持 MCPTT、MCVideo、MCData 三种关键通信服务服务器功能的应用服务器 [§1]。

一句话翻译：UE 里装了个管群的客户端（GMC），后端有个专门管群的服务器（GMS），三种业务服务器也能跟 GMS 打交道，大家按同一套协议语言沟通 [§1]。

还有个大前提：组管理只在 UE 运行于网络之上（即联网）时适用 [§1]。

从角色分工看，规范定义了三类功能实体：组管理客户端（GMC）、组管理服务器（GMS），以及 MCPTT 服务器、MCVideo 服务器、MCData 服务器这三种 MCS 服务器 [§5.1]–[§5.5]。其中 GMS 负责托管群组文档，GMC 和 MCS 服务器都可以在 GMS 上管理这些文档 [§4][§6.1]。GMS 扮演的角色是 XCAP 服务器，同时也是 OMA 定义的 Group XDMS [§5.2]。

这套组管理机制和具体的业务协议是配套的。MCS 组文档在 MCPTT、MCVideo、MCData 三种服务中的使用，分别由 TS 24.379、TS 24.281、TS 24.282 描述 [§7.2.1]。也就是说，把群建好之后，群里怎么说话，是那三份规范的事（见第 6 节）。

另外，这套协议横跨运营商网和互联网边界：规范专门定义了如何访问别的 MCS 服务商名下的群文档（GMS 转发请求的程序）、HTTP 请求里的身份认证、以及 SIP 失败时的处理方法 [§6.2.5.3]–[§6.2.5.5]。

## 3. 核心概念大白话

先把黑话翻译一遍，后面就不卡壳了。

**GMC（组管理客户端）**——UE 里管群的“管家 App”。它不负责群里的通话，只负责建群、改名单、读配置。要合规，GMC 必须扮演 XCAP 客户端（按 IETF RFC 4825 的规定）和 OMA 定义的 XDMC 角色 [§5.1]。

**GMS（组管理服务器）**——后端的“群管理中枢”，负责把每个群的配置文档托管好，响应客户端的读写请求。它必须扮演 XCAP 服务器（RFC 4825）和 OMA 的 Group XDMS [§5.2]。

**组文档（Group document）**——每个群的“电子档案”。标准说，MCS 组文档沿用 OMA 的 Group 规范来描述 [§7.2.1]。这份文档里装着这个群的名字、结构、成员名单等所有家当。文档里还包含 `<list-service>` 元素，它必须带一个 `uri` 属性，还可能带显示名、列表、规则集等内容 [§7.2.2]。

**组成员**——群档案里的成员条目，代表哪些 UE 或哪些人属于这个群。成员的增加、删除、修改就是对组文档元素的增删改，都有对应的专门程序（见第 5 节）[§6.3.6]–[§6.3.8]。

**订阅与通知**——你提前“登记”关心某个群，之后群配置一变，服务器就主动通知你。订阅与通知由 §6.3.13 规定：GMC 或 MCS 服务器订阅组文档变更，GMS 在变更后发通知，还能替 GMC 做订阅代理 [§6.3.13]。

两个细节值得记住。其一，规范注明，MCS 组文档里可以包含来自任何命名空间的额外属性和元素，只要符合 MCS 组文档的 XML  schema 就行 [§7.2.2]。其二，因为历史原因，有些元素名或属性名里带着 “mcptt” 字样，但它们并不专属于 MCPTT，MCVideo、MCData 等任何 MCS 服务都能使用 [§7.2.2]。名字带口音，不影响它是通用的。

## 4. 一次建组与加人怎么走

拿消防支队建一个“城南救援组”举例。

**第一步，创建组。** 指挥中心在调度台上发起，走组文档创建程序（Group document creation procedure）[§6.3.2]。客户端这边分两条路：普通客户端（GC）走它的客户端程序 [§6.3.2.2.1]，GMC 走自己的客户端程序 [§6.3.2.2.2]，GMS 在服务端处理 [§6.3.2.3]。这份规范里，GC 是通用客户端角色，它的程序 GMC 和 MCS 服务器都能用 [§6.2.2.1]；此外，GMC 和 MCS 服务器也都有各自的专属客户端程序 [§6.2.3][§6.2.4]。

**第二步，配成员。** 组文档建好后，往名单里加人、删人、换人，对应的是组文档元素（Group document element）的创建或替换 [§6.3.6]、删除 [§6.3.7]、获取 [§6.3.8] 这三套程序，每一步同样分客户端和 GMS 两侧。想改文档里的属性（比如群显示名），走属性创建或替换程序 [§6.3.9] 和属性删除程序 [§6.3.10]。

**第三步，下发组配置。** 组文档托管在 GMS 上，GMC 和 MCS 服务器通过在 GMS 上管理这些文档来让配置生效 [§4][§6.1]。

**第四步，成员可用。** 当客户端需要访问某个已知群 ID 的现有组文档时，它会把 HTTP 请求的 Request-URI 指向一个 XCAP URI——这个 URI 用群 ID 来定位文档，而 XCAP 根 URI 则用客户端本地配置好的那个 [§6.2.2.2]。有了这张“门牌号”，组里的终端就能按配置参加调度业务了。

还有个安全细节：GMC 发 HTTP 请求必须走 TLS 加密连接，方式按 TS 24.482 附件 A 对 UE 中 HTTP 客户端的规定执行 [§6.2.3]；MCS 服务器也按该附件对网元中 HTTP 客户端的规定发请求 [§6.2.4]；GMS 则按该附件对 HTTP 服务器的规定处理收到的请求 [§6.2.5.1]。一句话：从客户端到服务器，全程加密、按统一规矩收发 [§6.2.2]。

## 5. 关键时刻的能力

规范把群的一生拆成了很多标准动作，关键时刻都能派上用场：

**临时组**——救援现场临时拉一个小组，任务结束就解散，规范有专门的临时组建立 [§6.3.14] 与解散 [§6.3.15] 程序；组文档的创建 [§6.3.2] 与删除 [§6.3.5] 是底层的文档动作。

**组重组**——比如把 A 组一半人划给 B 组。这类重组通过组文档更新 [§6.3.4] 和组文档元素的增删改 [§6.3.6]–[§6.3.8] 组合完成：更新文档结构、替换成员元素。成员怎么分组的语义由业务决定，协议负责把变更可靠地做下去。

**成员加入 / 离开 / 移除**——这是高频动作，规范专门准备了元素创建或替换 [§6.3.6]、元素删除 [§6.3.7]、元素获取 [§6.3.8] 三套程序，分别处理“加人/换人”“踢人”“查名单”。每一类变更都是客户端一侧发起、GMS 一侧处理 [§6.3.6.2]–[§6.3.8.3]。

**组配置变更通知**——配置改了，得让关心这个群的各方知道。规范里有获取组文档的程序 [§6.3.3]，配合订阅机制，变更后相关方可按程序重新获取最新文档。


![图 4](figs/24481-图4_配置变更与通知.svg)

*图 4 · 组配置变更与通知：改了配置，谁收到通知。*

**读取组文档**——除了建和改，读也是标准动作：获取组文档程序同样分客户端 [§6.3.3.2]、MCS 服务器 [§6.3.3.3]、GMS [§6.3.3.3] 几个侧面。值得一提的是，获取某个群 ID 的现有组文档时，用的是第 4 节说的那套 XCAP URI 门牌号机制 [§6.2.2.2]。

还要多说一句能力差异：规范对 GMC 分了“必须支持”和“可以支持”。比如获取组文档是必须 [§5.1]，创建、更新、删除、元素的增删改取、属性的增删改取、以及 6.3.11、6.3.12、6.3.14、6.3.15 的若干程序都是“可以支持”，而订阅与通知（6.3.13.2.1）与排除成员的文档获取（6.3.16.2）是“必须支持” [§5.1]。GMS 侧同样有自己的义务清单，须支持 XCAP 服务器与 Group XDMS 角色 [§5.2]。这意味着不同终端的组管理能力可以有差异，标准允许“最小实现”和“增强实现”共存。

## 6. 组管理 vs 业务协议的区别

这是最容易混淆的地方，一句话：**TS 24.481 管“群本身”，业务协议管“群里的呼叫”。**

打个比方：TS 24.481 是“花名册管理员”，负责把每个群建好、成员名单维护对、配置下发对；MCPTT、MCVideo、MCData 三种业务协议则是“群里的通话系统”，负责按下按键说话、发视频、传数据 [§1]。花名册对，通话才找得对人；但花名册本身不管你们在群里说了啥。

具体对应关系是：MCS 组文档在 MCPTT 服务里的使用看 TS 24.379，在 MCVideo 里看 TS 24.281，在 MCData 里看 TS 24.282 [§7.2.1]。所以你建群用的是 24.481 这套动作，建好之后“开始说话”，就轮到那三份协议上场。两套规范各管一段，衔接点就是这份组文档。

## 7. 它不管什么

划清边界，避免误用：

- **不管需求目标。** 这套规范是 Stage 3 的协议细节 [§1]，回答“怎么说话”，不回答“为什么要做这个功能、要覆盖哪些行业”这类 Stage 1 需求问题。
- **不管组内的通话内容。** 组管理管的是群配置和成员名单，不管群里的话音、视频、数据怎么传——那是 MCPTT、MCVideo、MCData 业务协议的事 [§7.2.1]。
- **不管传输和实现选型。** 规范规定了 GMC 必须走 TLS、请求格式、URI 规则这些“接口层”的规矩 [§6.2.3][§6.2.2.2]，但具体用什么硬件、什么数据库存组文档，属于实现自由。
- **不凭空规定后续程序细节。** 目录里 6.3.11、6.3.12 等后续组管理程序，以及 6.3.16 等条目，分别是属性获取、命名空间绑定获取、订阅与通知、临时组建立/解散、排除成员的文档获取 [§6.3.11]–[§6.3.16]。
