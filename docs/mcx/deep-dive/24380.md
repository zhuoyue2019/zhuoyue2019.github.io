# 3GPP TS 24.380 解读：MCPTT 媒体面控制——对讲机的话筒权，网里是怎么抢的

> 版本：v1.0 ｜ 更新：2026-10-28 ｜ 基线：TS 24.380 v19.1.0（Rel-19，2025-09）｜ 原文：whatthespec.net 抓取的关键条款

**TS 24.380 是 MCPTT（关键业务推送对讲）的媒体面控制协议，它规定了在群组通话中，说话权（Floor）如何被请求、授予、拒绝、排队以及释放的具体规则和消息格式 [§1]。**


![图 1](figs/24380-图1_信令面与媒体面.svg)

*图 1 · 信令面 vs 媒体面：呼叫消息走 SIP，话筒权走媒体面控制通道。*

## 1. 它要解决什么问题

想象一下，你正在使用一部普通的微信群语音通话。如果几个人同时说话，声音就会重叠，根本听不清谁在说什么。但在警察执法、消防救援或铁路运营等关键业务场景中，混乱的语音意味着灾难。我们需要一种机制，确保在任何给定时刻，**只有一个人**拥有“话筒权”，其他人只能听，不能插嘴 [§4.1.1.1]。

这就是“地板控制”（Floor Control）要解决的核心问题。在 MCPTT 中，这不仅仅是“静音”或“取消静音”那么简单，它是一个严格的协议过程。TS 24.380 规定了当有人按下 PTT（Push-To-Talk，按住说话）按钮时，网络内部如何传递这个请求，服务器如何判断谁有权说话，以及如果优先级更高的人（比如指挥官）要插话，系统如何无缝地打断当前说话者并切换话筒权 [§4.1.1.2]。

如果没有这套协议，群组通话就会变成“大杂烩”。TS 24.380 确保了对讲机最核心的体验：**有序、可控、可抢占**。它定义了“谁先说”、“谁必须等”、“紧急情况怎么插队”以及“说完怎么交接”的所有底层交互细节 [§1]。

## 2. 它在 MCX 家族中的位置

为了理解 TS 24.380，你需要知道它在 3GPP 关键通信（MCX, Mission Critical Communications）标准家族中的位置。MCX 标准分为几个阶段：

*   **Stage 1 (TS 22.179)**：定义需求。比如组呼要能快速建立、紧急呼叫要有最高优先级。
*   **Stage 2 (TS 23.379)**：定义架构。比如“需要哪个网元（MCPTT Server）来处理这些请求”。
*   **Stage 3 (TS 24.379 和 TS 24.380)**：定义协议细节。这才是我们今天要讲的。

在这个家族中，**TS 24.379** 和 **TS 24.380** 是一对搭档，都是 Stage 3 标准。
*   **TS 24.379 (Call Control)**：管“呼叫信令”。它基于 SIP 协议，负责处理“建立呼叫”、“释放呼叫”、“修改呼叫参数”等消息。它决定的是“通话是否存在”。
*   **TS 24.380 (Media Plane Control)**：管“媒体面控制”。它基于 RTCP 协议，负责处理“谁有资格发声”。它决定的是“声音是否被允许传输”。

简单来说，TS 24.379 像是一个电话总机，负责接通线路；而 TS 24.380 像是会议室的麦克风管理器，负责决定哪支麦克风是开着的，哪支是关着的。两者必须配合：TS 24.379 建立了通话通道，TS 24.380 才在这个通道上运行，管理话筒权 [§1, §5.1]。

此外，实际的语音数据（RTP 包）是媒体流本身，TS 24.380 不定义语音怎么编码（那是 RTP/UDP 和编码器的事），但它定义了控制这些语音流开关的“遥控器”协议 [§8.1.1]。

## 3. 核心概念大白话

在深入流程之前，我们需要拆解几个 TS 24.380 中的关键术语。这些术语听起来很专业，但本质都很直观。

### 3.1 地板控制 (Floor Control)
这里的“地板”（Floor）不是指地面的地板，而是指“发言权”或“话语权”。在会议中，“standing on the floor”意味着你正在发言。在 MCPTT 中，Floor Control 就是管理谁有权发送语音包、谁只能接收语音包的机制 [§4.1.1.1]。

*   **Floor Participant (地板参与者)**：即用户终端（UE）。每个拿着对讲机的人都是一个 Floor Participant。它负责发送“我想说话”的请求，并接收“你可以说话”或“请闭嘴”的命令 [§5.2]。
*   **Floor Control Server (地板控制服务器)**：即决策者。在联网模式下（On-network），这个角色由 MCPTT Server 扮演。它像一个交警，看着所有车的请求，决定谁可以通行 [§4.1.1.2]。

### 3.2 媒体面控制通道 (Media Plane Control Channel)
这是一个逻辑通道，专门用来传送 TS 24.380 定义的控制消息（如 Floor Request, Floor Granted）。它通常复用 RTP/RTCP 通道。你可以把它想象成对讲机里的一条“暗线”，平时不传语音，只传控制指令，告诉你的麦克风是开还是关 [§4.3]。

### 3.3 发言权状态
一个 Floor Participant 在通话中通常处于以下几种状态之一：
1.  **Idle (空闲/无权限)**：麦克风是关的，只能听。
2.  **Pending (等待中)**：你按下了 PTT 按钮，但服务器还没回应，或者你在排队。
3.  **Granted (已授权/说话中)**：服务器给了你权限，你的声音被发给所有人。
4.  **Revoked (被抢占)**：你正在说话，但高优先级的人来了，服务器强制让你闭嘴 [§6.2.4]。

### 3.4 抢占 (Pre-emption)
这是关键业务通信的灵魂。如果正在说话的警察优先级是 5，而正在说话的指挥官优先级是 10，当指挥官按下 PTT 时，系统应该立即打断警察，让指挥官说话。TS 24.380 详细规定了这种“打断”和“恢复”的过程 [§4.1.1.2]。

### 3.5 排队 (Queueing)
如果两个人同时按下 PTT，且优先级相同，怎么办？TS 24.380 支持排队机制。第一个人获得权限，第二个人进入队列。当第一个人说完（释放 Floor），服务器自动把权限给队列中的第二个人，而不需要第二个人再次按下 PTT [§4.1.1.2]。

## 4. 一次组呼的媒体面流程

让我们通过一个典型的场景，看看 TS 24.380 是如何工作的。假设有一个 5 人的消防小队正在进行组呼。

**场景：消防员 A 请求发言**

1.  **请求 (Request)**：
    消防员 A 按下 PTT 按钮。此时，A 的终端（MCPTT Client）检测到按钮事件。它不会直接开始发语音，而是先通过媒体面控制通道，向 Floor Control Server（MCPTT Server）发送一个 **Floor Request** 消息。这个消息里包含了 A 的身份和优先级信息 [§4.1.1.2, §6.2.4.3.5]。

2.  **决策与授予 (Grant)**：
    Server 收到请求。如果当前没人说话，或者 A 的优先级足够高，Server 会做一个决定：批准 A。
    *   Server 向 A 发送 **Floor Granted** 消息（告诉 A：你可以说了）。
    *   Server 向组内其他所有人（B, C, D, E）发送 **Floor Taken** 消息（告诉其他人：A 开始说了，你们安静） [§4.1.1.2]。

3.  **说话 (Talk Burst)**：
    A 收到 **Floor Granted** 后，终端会播放一个提示音（Permission Tone），并打开麦克风。A 的语音被编码成 RTP 包，发送给 Server，Server 再分发给 B-E。这个过程称为“Talk Burst”或“Media Burst” [§4.1.1.2]。
    在此期间，A 的状态机处于 "U: has permission" 状态 [§6.2.4.3]。

4.  **释放 (Release)**：
    A 说完话，松开 PTT 按钮。终端检测到松开事件，向 Server 发送 **Floor Release** 消息。Server 收到后，更新状态，表示当前 Floor 空闲 [§4.1.1.2]。


![图 2](figs/24380-图2_地板控制流程.svg)

*图 2 · 地板控制消息流程：请求 → 授予/拒绝/排队 → 说话 → 释放。*

**场景：消防员 B 在 A 说话时请求发言（普通优先级）**

1.  B 按下 PTT，发送 **Floor Request**。
2.  Server 发现当前 A 正在说话，且 B 的优先级不高。Server 有两种处理方式（取决于配置）：
    *   **拒绝**：Server 向 B 发送 **Floor Deny**。B 听到拒绝提示音，松开按钮或保持等待，直到下次尝试 [§4.1.1.2]。
    *   **排队**：如果启用了排队，Server 向 B 发送 **Floor Queue Position Info**（告诉 B：你在队列第 1 位）。B 进入 "U: pending Request" 状态，保持 PTT 按下或等待提示。当 A 释放 Floor 后，Server 自动向 B 发送 **Floor Granted**，B 无需再次操作即可开始说话 [§4.1.1.2, §6.2.4.4]。

## 5. 关键时刻的能力

TS 24.380 的设计重点在于处理非正常的、紧急的情况。

### 5.1 紧急抢占 (Pre-emptive Priority)

这是最关键的功能。假设 A 正在说话（优先级 5），指挥官 C（优先级 10）按下 PTT。

1.  C 发送 **Floor Request**。
2.  Server 检测到 C 的优先级高于 A。
3.  Server 向 A 发送 **Floor Revoke** 消息。
4.  A 的终端收到 **Floor Revoke** 后，**必须立即停止发送语音**，并可能播放一个“被抢占”的提示音。A 的状态从 "Granted" 变为 "Revoked" 或 "No Permission" [§4.1.1.2, §6.2.4.3.10]。
5.  Server 向 C 发送 **Floor Granted**，并向其他人发送 **Floor Taken**。
6.  C 开始说话。

这个过程必须在毫秒级完成，以确保指挥指令的实时性。TS 24.380 规定了 **Floor Revoke** 消息的处理逻辑，确保被打断的一方不会继续发送噪音 [§4.1.1.2]。

### 5.2 多说话者控制 (Multi-talker)

在某些场景下（如讨论组），允许两个人同时说话。TS 24.380 支持配置“最大同时说话者数量”（Maximum number of simultaneous talkers）。如果当前说话人数少于上限，新的 Floor Request 可以被直接授予，而不需要 Revocation（抢占） [§4.1.1.2]。但如果是“音频切断”（Audio Cut-in）模式，则严格遵循一对一原则。

### 5.3 离网媒体面控制 (Off-network Floor Control)

如果没有网络信号（Off-network），MCPTT 可以通过 D2D（设备到设备）或 P2P 方式直接通信。此时，没有中央服务器（Floor Control Server）。

*   **谁是决策者？** 当前正在说话的终端充当“临时 Floor Arbitrator”（仲裁者）。
*   **流程变化**：
    1.  A 正在说话，B 想说话。B 发送 Floor Request 给所有人（包括 A）。
    2.  A（作为临时仲裁者）收到请求，判断优先级。
    3.  如果 B 优先级高，A 发送 Floor Revoke 给 B（实际上是确认抢占），或者 A 自己停止说话并发送 Floor Release。
    4.  更准确地说，在离网模式下，Floor Control 消息直接在客户端之间交换。当前说话者（Floor Arbitrator）在授予权限后，角色会互换：新说话者变成新的 Arbitrator，原说话者变成 Participant [§7.1]。
    5.  这种去中心化的控制增加了复杂性，因为每个终端都需要监听控制消息并动态改变角色。

## 6. 媒体面控制 vs 信令控制的区别

很多初学者容易混淆 TS 24.379 和 TS 24.380。让我们用一个比喻来区分：

*   **TS 24.379 (SIP 信令)**：就像**餐厅服务员**。
    *   你打电话（SIP INVITE），服务员走过来，确认桌号，把菜单给你（建立呼叫）。
    *   你打完电话（SIP BYE），服务员走过来，收拾桌子（释放呼叫）。
    *   它处理的是**会话的生命周期**。

*   **TS 24.380 (媒体面控制)**：就像**麦克风管理员**。
    *   在服务员把桌子摆好后（呼叫建立后），麦克风管理员开始工作。
    *   你按 PTT（Floor Request），管理员给你一个绿色指示灯（Floor Granted）。
    *   老板走过来说话（Pre-emption），管理员立刻关掉你的灯，给老板打灯。
    *   它处理的是**媒体流的权限**。

**关键区别点：**
1.  **触发时机**：SIP 呼叫建立后，媒体面控制才真正开始活跃。SIP INVITE 中可能包含隐式的 Floor Request，但后续的动态切换全靠 TS 24.380 [§6.2.1]。
2.  **消息类型**：SIP 使用文本或 SDP 格式的控制消息；TS 24.380 使用基于 RTCP APP 的二进制控制消息，开销更小，实时性更强 [§8.1.1]。
3.  **独立性**：即使呼叫已经建立（SIP 状态为 200 OK）， Floor Control 状态也在不断变化。你可以在呼叫期间不断切换说话者，而不需要重新建立 SIP 呼叫 [§4.1.1.2]。

此外，TS 24.380 还定义了**预建立会话 (Pre-established Session)** 上的呼叫控制。为了加快关键业务呼叫的建立速度，系统可以预先建立 SIP 会话和媒体通道。TS 24.380 规定了如何在这些预建立的通道上启动实际的通话和 Floor Control [§9.1]。

## 7. 它不管什么（边界）

明确 TS 24.380 的边界，有助于避免误解：

1.  **不管语音编码**：TS 24.380 不规定语音是用 AMR、Opus 还是 EVS 编码。它只控制这些编码后的数据包是否被发送。编码参数由 SDP（在 TS 24.379 中）协商 [§1, §8.1]。
2.  **不管网络传输细节**：它不规定 RTP 包如何在 IP 网络中路由，也不规定 MBMS（多媒体广播多播服务）的具体空中接口细节，只规定在 MBMS 承载上如何发送 Floor Control 消息 [§10.1]。
3.  **不管安全加密算法**：虽然 TS 24.380 提到了媒体面安全（Media Plane Security）的接口和流程，但具体的加密算法（如 SRTP）和密钥管理是由 TS 33.180 和 TS 23.379 规定的。TS 24.380 只是说“如果启用了安全，你要按这个流程走” [§5.2, §13]。
4.  **不管用户界面**：它不规定 PTT 按钮长什么样，也不规定提示音具体是什么声音（是滴滴声还是蜂鸣声），只规定“必须产生一个指示” [§4.1.1.1, §6.2]。
5.  **不管 Stage 1 需求**：它不讨论“为什么需要 5 秒建立”，只讨论“如何建立” [§1]。

## 8. 怎么往下读

如果你想深入理解 MCPTT 的实现或标准细节，建议按以下顺序阅读：

1.  **本篇 (TS 24.380)**：理解 Floor Control 的状态机和消息。重点关注 **Clause 6 (On-network floor control)** 和 **Clause 7 (Off-network floor control)**，以及 **Clause 8 (Coding)** 中的消息格式。
2.  **TS 24.379 (MCPTT Call Control)**：理解 SIP 信令流程。特别是 **Clause 6 (Call Setup)** 和 **Clause 7 (Call Release)**，看 SIP 消息中如何携带 Floor Control 相关的参数（如隐式请求）。
3.  **TS 23.379 (MCPTT Architecture)**：理解网元关系。搞清楚 Controlling MCPTT Function、Participating MCPTT Function 和 MCPTT Client 之间的交互逻辑。
4.  **TS 22.179 (Requirements)**：如果你想知道“为什么”要有抢占和排队，去这里找业务需求。
