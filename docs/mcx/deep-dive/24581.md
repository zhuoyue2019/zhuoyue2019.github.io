# 3GPP TS 24.581 解读：MCVideo 媒体面控制——视频画面谁先传，网里是怎么排的

> 版本：v1.0 ｜ 更新：2026-10-28 ｜ 基线：TS 24.581 v19.2.0（Rel-19，2026-06）｜ 原文：whatthespec.net 抓取的关键条款


**TS 24.581 是 MCVideo（任务关键视频）的媒体面控制协议，规定视频画面谁先传、怎么拉取推送、多路画面怎么排。**


**语音呼叫拼的是“谁先说话”，视频呼叫还要拼“谁先给画面”。MCVideo 面对的场景更硬核：多路现场画面、调度台要看现场、前端要推画面，都要在媒体面上写死规则 [§1]。**

举个生活类比：语音群呼像“一群人在对讲机里说话”，MCVideo 群呼像“多个摄像头同时开直播”。如果不在媒体面上定规矩，就会出现：所有人都喊“我先说”，画面乱成一锅粥；紧急画面被普通画面挤得播不出来；调度台想看某个现场，却没人给他拉画面。

所以 24.581 要解决的问题很具体：

- **多路画面怎么排**：在视频组呼里，任意时刻允许有多个组成员传视频，“最多同时传几路”由群组配置数据配好，不是拍脑袋决定 [§4.1.1.1]。其余组员被邀请接受画面，但**每个接收方可以自己选接不接，接了以后随时可以结束接收** [§4.1.1.1]。
- **谁有权说话（传画面）**：想传画面的人必须先拿到“传输许可”，这个许可由传输控制服务器拍板 [§4.1.1.1]。
- **调度台要画面**：调度台可以主动拉取某个前端的画面，前端也可以在关键时刻把画面推上去 [§4.1.1.2][§4.1.1.3]。
- **紧急画面优先**：当画面资源满了，新请求可以按优先级“踢掉”低优先级的在传画面，或者排队等位 [§4.1.1.2]。

这个规范适用于支持 MCVideo client 的终端（UE），以及支持媒体分发功能和传输控制服务器的 MCVideo 服务器 [§1]。它的服务对象不只是公共安全，还包括公用事业公司、铁路等一般商业应用 [§1]。

## 1. 它在 MCX 家族中的位置

3GPP 的 MCX 家族分三层：Stage 1 讲“要什么”（需求），Stage 2 讲“有哪些功能实体”（架构），Stage 3 讲“消息怎么传、流程怎么跑”（细节实现）。TS 24.581 属于 Stage 3，把 TS 23.281（架构）里定义的角色落到具体流程上：它明确说，功能实体要和 stage 2 架构文档 TS 23.281 里描述的 MCVideo 角色对上 [§5.1]。

它和 TS 24.281 是一对搭档：24.281 管“呼叫怎么建立、怎么修改、怎么释放”（信令面），24.581 管“呼叫建立之后，画面在媒体面上怎么传、谁有传输权”（媒体面）。一个管“打电话”，一个管“接通以后怎么说话”。

再打个比方：TS 23.281 像乐谱的总纲，TS 24.281 像排练时的“开始/暂停”手势，TS 24.581 像乐队指挥手里那根“谁先出声”的指挥棒。三者缺一不可。

## 2. 核心概念大白话

### 传输控制：媒体面上的“主持人”

在 MCVideo 里，有两类直接演员：**传输参与者**（在 MCVideo client 里做传输和接收控制动作）和**传输控制服务器**（传输和接收控制的决策者） [§4.1.1.1]。

- **网内模式（on-network）**：传输控制服务器位于具有控制角色（controlling role）的 MCVideo 服务器里 [§4.1.1.1]。
- **网外模式（off-network）**：没有专门的传输控制服务器，**当前的视频发送者就扮演传输控制服务器** [§4.1.1.1]。

用会议室类比：网内模式像有一个专职主持人（控制服务器），谁举手发言由主持人定；网外模式像没有专职主持人，谁现在拿着话筒，就由他来维持秩序。

### 媒体面控制通道：带外“对讲机”

媒体面控制消息不藏在视频流里，而是走一条专门的控制通道。规范说，MCVideo 媒体面控制通道以及其上使用的协议，由本规范描述 [§12.1.2.1]。建立这条通道时，会协商媒体面控制通道的媒体级属性 [§5.2.1]。

生活类比：视频画面像主菜，媒体面控制通道像服务员——“菜好了没、先上哪道、哪桌先撤”，全靠服务员传递，不影响厨房做菜。

### 视频拉取与推送：谁主动谁先动

- **推送（push）**：前端在现场主动请求权限，拿到许可后把画面传上去 [§4.1.1.2]。
- **拉取（pull）**：调度台收到“新画面要来了”的通知后，主动点接收，向传输控制服务器请求接收媒体 [§4.1.1.2]。

类比：推送像现场民警主动喊“我这里情况紧急，我先说”；拉取像调度员喊“把三号路口的画面切给我看”。

### 环境查看与能力共享

MCVideo client 要支持作为传输参与者，提供视频发送、视频传输结束、视频接收、视频接收结束这些按钮事件给传输参与者 [§5.2.1]；同时要向用户提供提示手段（声音、显示等） [§5.2.1]。这些“按钮事件 + 声音/显示提示”让终端用户能感知媒体面状态，属于能力的一部分。规范还注明：终端用户操作视频发送、传输结束、接收、接收结束按钮只是功能示意，本规范不强制要求这些终端用户动作 [§4.1.1.1]。

### MBMS 子信道与 FEC

在支持 MBMS 的系统里，MCVideo client 要提供 MBMS 接口，并支持 MBMS 子信道控制流程 [§5.2.1]。MCVideo 功能可以对 RTP 媒体包做 FEC，自己生成修复包在 MBMS 子信道上发，也可以请 BM-SC 来做 FEC [§10.1]。类比：MBMS 子信道像“广播频道”，FEC 像“多发一份备份”，丢包了还能拼回来。

## 3. 一次视频组呼的媒体面流程

把一次视频组呼拆成五步，每一步都有明确消息。

### 步骤 1：发起

呼叫建立时的协商来自 TS 24.281 [§6.2.1]。应用和信令面发出 SIP INVITE 请求时，在“协商了隐式传输请求”的情况下，这个 INVITE 被视为一个**隐式的 Transmission Request** [§6.2.1]。注意：如果是重新加入一个已经在进行中的组呼（rejoin），INVITE 就不算隐式传输请求 [§6.2.1]。

类比：你举着手走进会议室，这个“走进来”的动作本身就被当成一次发言申请；但如果你是中途回来拿东西，就不算。

### 步骤 2：传输控制授权

任一时刻，组成员都可以请求传输许可。如果“同时传视频的组员上限”还没满，用户点击视频发送按钮，传输参与者就向传输控制服务器发送 **Transmission Request** [§4.1.1.2]。服务器决定允许，就回 **Transmission Granted** [§4.1.1.2]。同时，服务器向其他组员发 **Media Reception Notification**，告诉他们“有新画面要来了” [§4.1.1.2]。

用户拿到许可后，client 会生成许可提示音（permission tone）告诉用户“视频开始传了” [§4.1.1.2]。

### 步骤 3：画面上行

拿到许可后，媒体包（编码后的音频流和视频流）先发到控制角色的 MCVideo 服务器，再由它分发给本组所有接收者 [§4.1.1.2]。这个“先到服务器、再由服务器分发”的设计，让传输控制服务器能统一管理谁在传、谁在收。

### 步骤 4：多方收看

接收方收到 Media Reception Notification 后，如果“同时接收的最大视频流数”还没满，client 会生成告警提示音（new video coming tone）提醒用户“有新画面要来了” [§4.1.1.2]。用户点视频接收按钮表示接受，传输参与者向传输控制服务器发 **Receive Media Request**；服务器同意，就回 **Receive Media Response** [§4.1.1.2]。

### 步骤 5：结束

- 发送方想结束：点视频传输结束按钮，传输参与者发 **Transmission End Request**，告知服务器“我传完了” [§4.1.1.2]。从 Transmission Granted 开始到 Transmission End Request 结束的这个循环，就叫“一次视频传输” [§4.1.1.2]。
- 接收方想结束：点视频接收结束按钮，传输参与者发 **Media Reception End Request**，告知服务器“我不看了” [§4.1.1.2]。

## 4. 关键时刻的能力

### 紧急视频：优先级“踢人”或排队

当“同时传视频上限”已经满了，还有人说“我有重要画面”。传输控制服务器有几种处理办法 [§4.1.1.2]：

1. **踢人**：如果新请求的优先级高于任何一路在传视频，服务器向优先级最低的那路发送者发 **Transmission Revoke**，打断它；当前传输参与者发 Transmission End Request 结束这次传输；然后服务器给新请求回 Transmission Granted，并给其他组员发 Media Reception Notification，新的视频传输开始 [§4.1.1.2]。
2. **拒绝**：如果新请求优先级不够高，且没有用排队，服务器发 **Transmission Deny**，用户端生成拒绝提示音（reject tone），在传画面继续 [§4.1.1.2]。
3. **排队**：如果用了请求排队，服务器发 **Transmission Queue Position Info**，告诉用户“暂时没许可，但你的请求已排队，等在传画面结束就有机会”，用户端生成“排队中”提示；在传画面继续 [§4.1.1.2]。

类比：会议室里话筒全被占用了，紧急情况要么让优先级最低的人先闭嘴（踢人），要么让紧急的人先来排队等话筒（排队），或者直接告诉紧急的人“现在没空位”（拒绝）。

### 视频拉取与推送


![图 3](figs/24581-图3_视频拉取与推送.svg)

*图 3 · 视频拉取 vs 视频推送：调度台主动要画面 vs 前端主动传画面。*

拉取的关键是“接收方主动”：调度台收到 Media Reception Notification 后，点接收，发 Receive Media Request [§4.1.1.2]。推送的关键是“发送方主动”：前端点发送按钮，发 Transmission Request [§4.1.1.2]。两者都经过传输控制服务器授权，保证多路画面不会抢成一团。

### 传输控制排队与计时器

排队不是“无限等”。规范定义了计时器 T100（Transmission Request） [§6.2.4.4.3]。T100 的推荐值可在 TS 24.484 里配置 [§11.1.1]。启动时机包括：传输参与者发送 Transmission Request 消息；以及当应用层和信令面发起会话传输配置、作为隐式传输请求时 [§11.1.1]。正常停止：收到 Transmission Granted、Transmission Rejected 或 Transmission Queue Position Info 消息 [§11.1.1]。超时处理：如果计数器小于 C100 的上限，就重新发送 Transmission Request，并把计数器加 1；如果达到上限，就发一个 Transmission Rejected 消息（NOTE 1） [§11.1.1]。另外，当 application 层的“mc_implicit_request”元素用来发起会话传输配置作为隐式传输请求时，也会启动 T100 [§11.1.1]。

另一个计时器 T101（Transmission End Request）管“传输结束请求” [§6.2.4.6.2]，其值同样可在 TS 24.484 配置 [§11.1.1]。

类比：排队取号后，等太久没人理就叫下一轮重试；重试次数太多就告诉自己“今天没戏”。

### 多路画面的传输控制

核心规则就三条：上限由群组配置定 [§4.1.1.1]；新请求按优先级决定是踢人、拒绝还是排队 [§4.1.1.2]；接收端也能按自己的上限选择接不接 [§4.1.1.1]。这样保证了“谁先传”不是靠抢，而是靠规则。

## 5. 媒体面控制 vs 信令控制

这两个容易混。用类比说：信令面像“写信约人开会”，媒体面像“开会时谁先发言”。

- **TS 24.281（信令控制）**：管 SIP 消息，管呼叫建立、修改、释放。SIP INVITE 在“协商了隐式传输请求”时，还能顺带隐式表达一次传输请求 [§6.2.1]。
- **TS 24.581（媒体面控制）**：管媒体面上的传输权。所有传输控制消息（Transmission Request/Granted/Revoke/Deny/End Request 等）都在媒体面上跑，走媒体面控制通道 [§4.3.1]。

规范还明确：媒体面控制协议基于 RTCP Application Packets（RTCP: APP，见 IETF RFC 3550），但媒体面控制消息不遵守 compound RTCP 包规则，每个媒体面控制消息就是一个 RTCP: APP 包；这些包不放在 compound RTCP 包里发，但一个 IP 包里可以装多个媒体面控制消息 [§9.1.1]。每个媒体面控制协议的前 32 位字结构按 §9.1.2 描述 [§9.1.1]。

## 6. 它不管什么

TS 24.581 不是“万物规范”，边界很清楚：

- **不管 Stage 1 需求**：它不是需求文档，而是把需求落到媒体面流程。
- **不管视频编解码**：它管的是“编码后的音频流和视频流怎么传”，编码本身不在这个规范里 [§4.1.1.2]。
- **不管实现选型**：终端厂商用什么芯片、服务器用什么操作系统，它不管。
- **安全机制另见**：需要媒体面安全时，MCVideo client、控制角色 MCVideo 功能、参与角色 MCVideo 功能、非控制角色 MCVideo 功能要执行 clause 13 的附加流程；媒体面安全的要求见 TS 33.180 [§13]。MCVideo client 也要支持 clause 13 规定的媒体面安全 [§5.2.1]。


**它只管“画面传输权怎么分配、媒体面控制消息怎么跑”，别的都不越界。**
