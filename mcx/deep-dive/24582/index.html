    3GPP TS 24.582 解读：MCData 媒体面控制——短数据和文件，网里是怎么排队发的¶

    版本：v1.0 ｜ 更新：2026-10-28 ｜ 基线：TS 24.582 v19.0.0（Rel-19，2025-10）｜ 原文：whatthespec.net 抓取的关键条款

    TS 24.582 是 MCData（关键任务数据）的媒体面控制协议，它规定了短数据、文件和 IP 连接在媒体面上具体怎么发、怎么控、谁有权限发。

    1. 它要解决什么问题¶

    如果你做过无线电对讲，你知道有个“PTT”（按下讲话）键。在语音通信中，如果两个人同时按，声音会混在一起，谁也听不清。所以无线电协议规定了“谁先按谁说话，后按的必须等”。

    但在数据通信里，情况更复杂。数据不像声音那样能“抢话筒”，它是字节流。在 MCData 这种关键任务场景（比如警察、消防、铁路调度）中，数据通信不能像普通微信那样随意乱发，否则网络会瘫痪，或者重要指令被垃圾消息淹没。

    TS 24.582 解决的核心问题就是：在媒体面（真正传数据的那条路）上，怎么控制谁有资格把数据发出去，以及发出去的数据该怎么走。

    具体来说，它管三件事： 1. 短数据（SDS）：像短信一样短，但要求高。谁先获得“发送权”？怎么防止消息风暴？ 2. 文件分发（FD）：发照片、图纸、地图。怎么确保文件完整送到？ 3. IP 连接：建立一条纯粹的 IP 数据通道，让应用层随便跑数据，但底层的建立和释放要有规矩。

    想象一下，媒体面就像一条高速公路。TS 24.582 不是规定车怎么造（那是应用层的事），也不是规定收费站怎么收钱（那是信令层的事），它规定的是：哪些车有通行证（发送控制），车在高速上怎么跑（媒体面协议），以及车到了目的地怎么确认签收（处置通知）。 [§1]

    2. 它在 MCX 家族中的位置¶

    要理解 TS 24.582，得先知道它在 3GPP 关键任务通信（MCX，Mission Critical Communication）大家族里的位置。

    • Stage 1 (TS 22.282)：画大饼。定义业务需求，比如“警察需要一键通”、“消防员需要发图片”。
    • Stage 2 (TS 23.282)：画图纸。定义架构，也就是 MCData 系统里有哪些功能实体、它们怎么分工。
    • Stage 3 (TS 24.282、TS 24.582)：做菜。定义具体协议：24.282 管信令（“打电话”的过程：怎么建立呼叫、怎么振铃、怎么挂断），24.582 管媒体面（“牛排”本身怎么端上桌）。

    关键点：TS 24.582 是 Stage 3 的媒体面控制规范。

    它和 TS 24.282 是配套使用的。TS 24.282 负责“建立管道”（信令），TS 24.582 负责“在管道里灌数据”（媒体面控制）。 * 信令走 SIP 协议（Session Initiation Protocol）。 * 数据走 MSRP 协议（Message Session Relay Protocol）或 IP 协议。

    TS 24.582 适用于支持 MCData 客户端功能的用户设备（UE）和 MCData 服务器。它既适用于公共安全（警察、消防），也适用于一般商业应用（公用事业、铁路）。 [§1]

    3. 核心概念大白话¶

    在深入流程之前，有几个概念必须用大白话讲清楚。

    3.1 媒体面控制通道¶

    你可以把媒体面想象成一个“专用快递柜”。 * MSRP：这是快递柜的操作说明书。它规定了怎么把包裹（数据）放进去，怎么通知收件人取件。 * IP Connectivity：这是一种特殊的快递柜，里面可以放任何符合 IP 标准的包裹，甚至可以直接在柜子里面进行双向传送（像管道一样）。

    3.2 短数据 (SDS, Short Data Service)¶

    就是“关键任务短信”。 * Standalone SDS（独立短数据）：就像发微信短信，发完就结束。不需要先建立长连接。 * SDS Session（短数据会话）：就像建立了一个群聊语音通话，在这个期间，群里的成员可以轮流发短消息。会话结束前，发送权是动态分配的。

    关键区别：独立短数据是一次性的；会话短数据是持续性的，且受会话内的“发送控制”约束。 [§4.1.1]

    3.3 文件分发 (FD, File Distribution)¶

    就是“关键任务文件传输”。 * 你可以发一张现场照片给指挥中心。 * 你可以发一份维修手册给现场工程师。 * 强制下载 (Mandatory Download)：网络可以命令接收方“必须下载”，不管你现在忙不忙。这在紧急情况下很有用。 [§4.1.2]

    3.4 IP 连接 (IP Connectivity)¶

    这是一种更底层的连接。 * 一旦建立，UE 和服务器之间就有一条纯粹的 IP 通道。 * 应用层（比如一个定制的指挥系统）可以直接在上面跑自己的协议，不需要再关心 MSRP 怎么封装。 * 注意：Rel-19 的 IP 连接与 Rel-16 不兼容。这意味着如果你用老设备，可能连不上新网络的 IP 连接。 [§4.1.4]

    3.5 发送控制与接收控制¶

    • 发送控制：谁有资格发？在会话中，可能只有组长能发，或者只有当前持有“话筒”的人能发。TS 24.582 规定了在媒体面上如何验证和传递这个“资格”。
    • 接收控制：谁能收？虽然主要是发送方决定发给谁，但接收方也需要确认自己有能力接收（比如存储空间、网络带宽）。

    4. 一次短数据发送的媒体面流程¶

    让我们通过一个具体的例子来理解短数据（SDS）是怎么发的。假设警察 A 要独立发送一条短数据给警察 B（Standalone SDS）。

    图 1 · 信令面 vs 媒体面（数据）：信令走 SIP，数据发送权走媒体面控制。

    步骤分解：

    1. 准备阶段（信令层，TS 24.282 管）： 警察 A 的 UE 发起呼叫。网络建立了一条媒体通道。此时，UE 知道对方是谁，也知道了媒体通道的参数（比如 IP 地址、端口）。

    2. 建立 MSRP 连接（TS 24.582 核心开始）： 一旦媒体面建立，MCData 客户端（UE）需要建立 MSRP 会话。

      • 发送方（UE）作为 MSRP 客户端。
      • 它需要确定自己是“主动端”还是“被动端”。这由信令层协商的 SDP（Session Description Protocol）中的 a=setup 属性决定。
      • 如果 UE 是“主动端”，它需要发送一个空的 MSRP SEND 请求。
      • 为什么要发空包？ 这是一个握手动作。告诉服务器：“我连上了，我准备好了。” 服务器收到后回复 200 OK。 [§7.1.2.1]

    3. 生成数据负载（TS 24.582 核心）： 现在 UE 可以真正发数据了。

      • 信令负载 (Signalling Payload)：包含控制信息，比如“这是一个短数据消息”、“消息 ID 是 123”、“这是给谁看的”。
      • 数据负载 (Data Payload)：包含真正的短数据内容，比如“现场情况紧急”。
      • 关键点：在同一个 MSRP SEND 请求中，信令负载和数据负载是分开的 Body（主体）。
        • Body 1: 媒体控制信息（信令负载）。
        • Body 2: 实际数据（数据负载）。 [§4.1.1]

    4. 发送与保护：

      • 信令负载：在每一跳之间保护。比如 UE 到服务器 A 用一把钥匙加密，服务器 A 到服务器 B 用另一把钥匙加密。这保证了控制信息的完整性，但中间节点可以解密以进行路由。
      • 数据负载：端到端保护。UE 用一把钥匙加密，只有目的地 B 能解密。中间的服务器完全看不懂数据内容，只是透传。 [§4.2]

    5. 接收与确认： 接收方 B 收到 MSRP SEND 请求。

      • 它先解析信令负载，确认这是发给自己的短数据。
      • 然后解密数据负载，显示内容。
      • 如果 B 同意接收（或者根据策略自动接收），它会发送一个处置通知 (Disposition Notification)。
      • 这个通知也是通过 MSRP 发送的。它告诉发送方：“我收到了，我看懂了，我处理了。” [§6.1.2.5]

    图 2 · 短数据 SDS 发送控制流程：编辑 → 发送控制 → 转发 → 确认。

    如果是会话中的短数据呢？ 如果 A 和 B 正在一个“SDS 会话”中（类似群聊），流程类似，但有一个关键区别：发送权。 * 在会话中，不是谁想发就能发，只有有相应权限的参与成员才能发起短数据发送，直到会话结束 [§4.1.1]。 * 只有在持有发送权的客户端，其发出的 MSRP SEND 请求才会被网络正常处理。如果没有发送权，网络可能会丢弃或拒绝。 [§4.1.1]

    5. 关键时刻的能力：文件分发、紧急数据与 IP 连接¶

    5.1 文件分发 (FD)：大包的快递¶

    文件分发比短数据复杂，因为文件可能很大（比如 10MB 的图片）。

    • 流程：

      1. 信令层建立媒体面。
      2. 发送方 UE 建立 MSRP 连接。
      3. 发送方将文件切分成多个部分（File Portions）。
      4. 通过 MSRP SEND 请求发送文件部分。
      5. 接收方接收并重组文件。
      6. 接收方发送处置通知，确认文件完整接收。 [§7.1]

    • 强制下载 (Mandatory Download)： 这是一个非常强大的功能。如果标记为“强制”，网络会确保文件必须被下载，即使接收方设备当前处于“静音”或“低优先级”状态。这在发送紧急地图或指令时至关重要。

      • 在信令面建立时，会携带 Mandatory Download 标志。
      • 在媒体面，这个标志会影响接收方的处理逻辑：它不能被忽略。 [§4.1.2]

    • 元数据 (Metadata)： 文件可以附带元数据，比如“这是一张现场照片，拍摄于 10:00”、“这是维修手册第 3 章”。这些元数据也在信令面协商，并在媒体面传输。 [§4.1.2]

    图 3 · 文件分发媒体面流程：上传 → 分发 → 下载 → 完成确认。

    5.2 处置通知：告诉对方“收到了吗”¶

    短数据发出去，发送方想知道对方收没收到、看没看。TS 24.582 用处置通知（SDS Notification）来做这件事 [§6.1.2.5]： * 接收方可以发“已送达”（DELIVERED）、“已读”（READ）、“已送达且已读”（DELIVERED AND READ）三种通知。 * 如果消息没能交付给用户或应用（比如接收方存储不足），发“未送达”（UNDELIVERED）通知。 * 通知类型由 SDS 处置通知类型信息元指明，发送与接收程序都在 §6.1.2.5 里 [§6.1.2.5.2]。

    5.3 IP 连接：纯粹的管道¶

    IP 连接是 TS 24.582 中一个比较特殊的服务。

    • 特点：

      • 它只提供 IP 层的连接。
      • 一旦建立，UE 和服务器之间就像有一根网线连着。
      • 应用层可以使用任何 IP 协议（TCP, UDP, QUIC 等）。
      • 不兼容 Rel-16：这是一个重要的版本边界。Rel-19 的 IP 连接机制与 Rel-16 不同，意味着新老版本设备在 IP 连接上可能无法互通。 [§4.1.4]

    • 建立流程：

      1. 信令层协商 IP 连接参数。
      2. 媒体面建立 IP 连接。
      3. 数据直接在 IP 层传输，不再经过 MSRP 封装。
      4. 释放时，信令层触发，媒体面的 IP 连接断开。 [§4.1.4]

    图 4 · 接收控制与 IP 连接：谁能收、IP 连接怎么建。

    6. 媒体面控制 vs 信令控制的区别¶

    很多初学者容易混淆 TS 24.582 和 TS 24.282。这里用一张表来厘清：

    特性 TS 24.282 (信令控制) TS 24.582 (媒体面控制)
    主要职责 建立/释放呼叫，协商参数 在已建立的通道上传输数据
    协议 SIP (Session Initiation Protocol) MSRP (Message Session Relay Protocol) / IP
    关注点 “我们要连吗？”“参数是什么？” “数据怎么发？”“谁有资格发？”
    数据内容 通常不包含业务数据（只有元数据） 包含业务数据（短数据、文件、IP 包）
    安全 信令保护（保护元数据） 媒体保护（保护业务数据和控制信息）
    类比 餐厅服务员点菜、结账 厨师做菜、服务员上菜

    关键点：TS 24.582 管的是“发送权”在媒体面上的体现。 在信令层，我们协商“这个会话允许发送短数据”。但在媒体面，TS 24.582 规定了当数据真正流动时，如何验证这个权限，以及如何处理权限变更（比如组长把发送权移交给副手）。 [§4.1.1]

    7. 它不管什么（边界）¶

    为了不让读者跑偏，必须明确 TS 24.582 不负责什么：

    1. 不管 Stage 1 需求：它不定义“警察需要什么样的功能”，那是 TS 22.282 的事。
    2. 不管文件内容本身：它不关心你发的是图片还是 Word 文档，也不关心图片分辨率。它只关心“这个文件包”怎么在网里走。
    3. 不管具体应用实现：它不规定你的 App 界面长什么样，也不规定你的 App 怎么解析图片。
    4. 不管底层网络细节：它不关心你是用 4G 还是 5G，是 Wi-Fi 还是卫星。它假设底层网络已经提供了可靠的 IP 传输。
    5. 不管信令细节：SIP 消息的具体格式、SIP 服务器的逻辑，那是 TS 24.282 的事。

    安全机制在哪里？ TS 24.582 定义了使用哪些密钥（CSK, GMK, PCK），但密钥的生成、管理和分发是在 TS 33.180 中定义的。 * CSK (Client-Server Key)：用于保护 UE 和服务器之间的信令负载。 * GMK (Group Master Key)：用于保护群组通信中的媒体数据。 * PCK (Pairwise Client Key)：用于保护一对一通信中的媒体数据。 TS 24.582 规定：“如果你要加密，就用这把钥匙。”但TS 33.180 规定：“这把钥匙是怎么来的，怎么换的。” [§10.1]

    8. 怎么往下读¶

    如果你想深入理解 MCData 的媒体面，建议按以下顺序阅读：

    1. 本篇 (TS 24.582)：理解媒体面控制的基本流程、MSRP 的使用、发送控制机制。
    2. TS 24.282 (信令控制)：理解信令层如何建立媒体面，如何协商 MSRP 参数，如何触发媒体面操作。这是 TS 24.582 的“上游”。
    3. TS 23.282（架构）与 TS 22.282（需求）：理解为什么需要这些功能，业务场景是什么。这是“为什么”。
    4. TS 33.180 (安全)：理解密钥管理和安全机制。这是“怎么保安全”。
    5. RFC 4975 (MSRP)：如果想看 MSRP 协议的细节，去读这个 IETF 标准。TS 24.582 是基于 MSRP 的。

    版本说明： 本文基于 TS 24.582 v19.0.0 (Rel-19, 2025-10)。 * Rel-19 新特性：IP 连接机制更新，与 Rel-16 不兼容。 * 注意：3GPP 标准更新频繁，具体实现时需确认最新的 errata（勘误表）。
